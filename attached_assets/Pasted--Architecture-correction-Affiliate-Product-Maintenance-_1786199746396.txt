# Architecture correction — Affiliate Product Maintenance

Do not implement the previous architecture yet.

The architecture report revealed that the existing Django `Product` model is NOT the actual product catalogue:

* `Product.objects.count() == 0`
* all 138 live products come from `products_*.py`
* the existing `Product` model also has static/catalogue fields and a `Category` FK
* it is already referenced by separate DB views, fallback logic and click tracking

Because of this, I do NOT want to repurpose/populate the existing `Product` model with 138 records merely to store affiliate maintenance state.

Implement the maintenance data as a separate model instead.

---

## 1. Create a dedicated maintenance model

Create a model with a clear name such as:

```python
class AffiliateProductState(models.Model):
    slug = models.SlugField(unique=True)
    price = models.DecimalField(...)
    availability = models.CharField(...)
    price_last_checked = models.DateField(null=True, blank=True)
```

Exact field definitions should follow the existing product data formats.

The `slug` is the stable link to `ALL_PRODUCTS_BY_SLUG`.

Do NOT create a ForeignKey to the existing `Product` model because the live Python catalogue does not currently have corresponding `Product` database records.

Do NOT create 138 records in the existing `Product` model.

The architecture should become:

```text
products_*.py
    |
    | static/base product information
    v
prepare_product_variants()
    |
    +-----------------------------+
    |                             |
    |                    AffiliateProductState DB
    |                    matched by unique slug
    |                             |
    +---------- effective override+
                  |
                  v
         effective runtime product
                  |
                  v
         apply_resolved_link()
                  |
                  v
         derive price levels
                  |
                  v
templates / JSON-LD / comparison tables / quick picks
```

The Python product files remain the source for static product information.

`AffiliateProductState` becomes the authoritative runtime source for:

* price
* availability
* price_last_checked

after a maintenance record exists.

---

# 2. Important: change the overlay order

The previously proposed order was:

```text
_overlay_db_values()
→ prepare_product_variants()
```

This is unsafe.

The architecture report confirms that `prepare_product_variants()` projects the default variant commercial fields onto the family-level product.

Therefore it could overwrite the database-maintained price and availability.

Use this order instead:

```python
product = deepcopy(python_product)

prepare_product_variants(product)

apply_affiliate_maintenance_override(product)

apply_resolved_link(product)

derive_price_levels(product)
```

Or the equivalent order supported by the existing code.

The important rule is:

> AffiliateProductState must override the final effective/default variant commercial values, not the other way around.

Add a regression test proving this for a product with `shape_variants`.

# 3. Availability label must remain consistent

The report shows that the frontend primarily displays:

```text
availability_label
```

rather than directly displaying:

```text
availability
```

This creates an important consistency requirement.

Example:

Python data:

```text
availability = OutOfStock
availability_label = "Tijdelijk uitverkocht"
```

Admin changes DB maintenance value to:

```text
availability = InStock
```

The public website must NOT produce:

```text
availability = InStock
availability_label = "Tijdelijk uitverkocht"
```

Therefore inspect `resolve_availability_label()` and `apply_resolved_link()` and make the effective label follow the effective database availability where a DB override exists.

Prefer one central normalization function.

Conceptually:

```python
AVAILABILITY_LABELS = {
    "InStock": "...existing appropriate available label...",
    "OutOfStock": "...existing appropriate unavailable label...",
}
```

However, reuse the site's existing wording and CTA behaviour instead of inventing new labels.

If the Python product does NOT yet have a database maintenance override, retain the current Python behaviour.

Add tests for:

```text
Python OutOfStock
DB InStock
→ frontend and JSON-LD both behave as InStock
```

and:

```text
Python InStock
DB OutOfStock
→ frontend and JSON-LD both behave as OutOfStock
```

# 5. Initial synchronization

Create a management command, for example:

```bash
python manage.py sync_affiliate_product_states
```

It should loop over `ALL_PRODUCTS_BY_SLUG`.

For each unique slug:

* create an `AffiliateProductState` record if it does not exist;
* initialize `price` from the effective/default Python price;
* initialize `availability` from the effective/default Python availability;
* normalize legacy availability values;
* import a genuine existing `price_last_checked` if one exists.

IMPORTANT:

If the Python product has no real `price_last_checked`, store:

```python
price_last_checked = None
```

Do NOT initialize it to today's date.

Running the sync command does not mean that the product has actually been manually checked.

A NULL `price_last_checked` should therefore put the product into the maintenance queue.

The command must be idempotent.

Running it a second time must NOT overwrite manually maintained database price/availability values by default.

Suggested behaviour:

```text
missing state record
→ create and initialize from Python

existing state record
→ leave manually maintained commercial values untouched
```

If useful, an explicit `--force` option may be added for development/testing, but ordinary production sync must never overwrite admin-maintained values.

Report:

```text
Python products found: 138
Unique slugs: ...
Maintenance records created: ...
Existing records retained: ...
Missing prices: ...
Missing availability: ...
Legacy OutofStock normalized: ...
Duplicate slugs: ...
Errors: ...
```

# 8. Do NOT rely on normal list_editable + admin action

The intended workflow is:

```text
Open maintenance page
→ open retailer URL
→ optionally edit price
→ optionally edit availability
→ select checked products
→ click one confirmation action/button
→ edited values are saved
→ selected rows get price_last_checked = today
```

Standard Django `list_editable` saving and admin actions are separate POST workflows.

Therefore do NOT assume that unsaved list-editable values will automatically be persisted when a normal admin action is executed.

Implement a small dedicated changelist form / custom admin view that processes:

* editable price;
* editable availability;
* row selection;
* confirmation;

in ONE atomic POST.

Keep this as close to standard Django Admin as possible.

Avoid building a separate frontend application.

Minimal custom admin template/form logic is acceptable and preferable to a confusing two-step:

```text
Save
→ select again
→ run action
```

# 9. Confirmation behaviour

For every SELECTED row:

### Price

If the submitted price differs from the stored price:

```text
save new price
```

If it is unchanged:

```text
retain current price
```

Do not interpret an accidentally blank input as an instruction to delete an existing price.

### Availability

If changed:

```text
save new availability
```

Otherwise:

```text
retain existing availability
```

### Check date

For every selected and successfully validated product:

```python
price_last_checked = timezone.localdate()
```

assuming this is implemented as a `DateField`.
