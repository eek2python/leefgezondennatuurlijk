We need to make the production database architecture of the Django website **Leef Natuurlijk & Gezond** durable and deployment-safe.

## Context

A production incident occurred after a deployment.

The Render production site returned HTTP 500 on product pages because Django code queried:

`AffiliateProductState.objects.in_bulk(...)`

but the Render SQLite database had not been migrated.

The exact production error was:

`django.db.utils.OperationalError: no such table: products_affiliateproductstate`

We manually ran on Render:

```bash
python manage.py migrate --noinput
```

After that:

```text
products
[X] 0001_initial
[X] 0002_affiliateproductstate
```

and the website worked again.

However, the current Render setup appears to use **SQLite without a Persistent Disk**.

`AffiliateProductState.objects.count()` currently returns:

```text
0
```

The local Replit database contains approximately 138 `AffiliateProductState` records.

This means the immediate incident is resolved, but the production database architecture is not durable. A future Render deployment/restart may recreate or lose the SQLite database.

The preferred target architecture is:

```text
Django on Render
      ↓
Render PostgreSQL
      ↓
persistent production data
```

with database migrations automatically executed as part of the Render deployment process.

## Objective

Create a **migration and deployment plan only** for moving the production environment from SQLite to Render PostgreSQL.

Do **not** deploy anything.
Do **not** create or modify the Render database.
Do **not** change production environment variables.
Do **not** delete or overwrite production data.

You may inspect and, if useful, make code/configuration changes locally that prepare the repository for PostgreSQL, but clearly separate:

* analysis
* proposed changes
* changes actually made locally
* production actions still required
