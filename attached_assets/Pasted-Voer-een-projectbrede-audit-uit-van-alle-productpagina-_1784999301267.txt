Voer een projectbrede audit uit van alle productpagina’s en productcategorieën
die varianten ondersteunen.

Aanleiding:

Voor de vershoudbakjespagina is recent de commerciële variantresolutie
verbeterd. De vergelijkingstabel gebruikt nu strikt de geselecteerde
displayvariant voor:

- affiliate-link;
- prijs;
- beschikbaarheid;
- capaciteit;
- ratingweergave.

Er resteerde daarnaast een mogelijk stale-value-risico in
`set_display_variant` of vergelijkbare logica: wanneer een nieuwe variant
een veld niet bevat, kan theoretisch een waarde van een vorige variant,
defaultvariant of productniveau blijven staan.

Doel van deze taak:

1. inventariseer alle productcategorieën met varianten;
2. controleer welke centrale en categorie-specifieke helpers zij gebruiken;
3. detecteer cross-variant fallbacks en stale-value-risico’s;
4. controleer productblok, vergelijkingstabel en JSON-LD op onderlinge
   consistentie;
5. voer alleen centrale en aantoonbaar veilige fixes uit;
6. rapporteer categorie-specifieke risico’s die niet veilig automatisch
   kunnen worden opgelost;
7. voeg herhaalbare tests toe.

==================================================
4. CONTROLEER IN-PLACE MUTATIE
==================================================

Zoek alle helpers die productdictionaries in-place wijzigen.

Controleer met name patronen zoals:

product["price"] = variant.get("price", product.get("price"))

of:

if variant.get("affiliate_url"):
    product["affiliate_url"] = variant["affiliate_url"]

Deze patronen zijn riskant, omdat oude waarden kunnen blijven staan.

Rapporteer per helper:

- wordt de brondata gemuteerd?
- wordt een shallow copy of deep copy gemaakt?
- kunnen waarden van een vorige variant blijven staan?
- wordt hetzelfde productobject meerdere keren binnen één request gebruikt?
- kan filtering de productdata voor een volgende rendering beïnvloeden?

Geef de voorkeur aan voorbereide kopieën of een aparte displaystructuur.

==================================================
5. GEWENSTE CENTRALE OPZET
==================================================

Wanneer veilig en passend, centraliseer de variantresolutie in herbruikbare
helpers.

Bijvoorbeeld:

resolve_display_variant(product, selection=None, size_filter=None)

resolve_variant_fields(product, display_variant)

prepare_product_for_display(product, display_variant)

resolve_commercial_fields(product, display_variant)

De voorbereidende output mag bijvoorbeeld bevatten:

{
    "source_product": product,
    "display_variant": display_variant,
    "display_variant_id": ...,
    "display": {
        "affiliate_url": ...,
        "price": ...,
        "currency": ...,
        "availability": ...,
        "price_last_checked": ...,
        "image": ...,
        "image_path": ...,
        "dimensions": ...,
        "usage": ...,
    },
}

Belangrijk:

- muteer de oorspronkelijke productdata niet;
- gebruik voor producten met varianten geen commerciële fallback naar een
  andere variant;
- gebruik productniveauvelden alleen voor producten zonder commerciële
  variantdata;
- gedeelde niet-variantafhankelijke velden blijven op productniveau.

Voer geen grote refactor uit wanneer categorieën fundamenteel verschillende
variantenlogica hebben. Rapporteer die dan apart.

==================================================
6. STRIKTE COMMERCIELE RESOLUTIE
==================================================

Voor ieder product met varianten geldt:

- prijs komt uitsluitend van de gekozen displayvariant;
- affiliate-link komt uitsluitend van de gekozen displayvariant;
- beschikbaarheid komt uitsluitend van de gekozen displayvariant;
- prijscontroledatum komt uitsluitend van de gekozen displayvariant;
- ontbrekende waarden blijven ontbrekend;
- geen fallback naar defaultvariant;
- geen fallback naar eerste variant;
- geen fallback naar een vorige variant;
- geen fallback naar productniveau wanneer productniveau verouderde
  variantdata kan bevatten.

Voor producten zonder varianten mogen productniveauvelden worden gebruikt.

Maak deze regels centraal wanneer dat veilig kan.

==================================================
7. PRODUCTKAARTCONTROLE
==================================================

Controleer per categorie:

- gebruikt de productkaart dezelfde displayvariant als de backend selecteert?
- gebruikt de koopknop exact de affiliate-link van die variant?
- wordt een ontbrekende link daadwerkelijk verwijderd?
- wordt een ontbrekende prijs daadwerkelijk gewist?
- wordt een ontbrekende beschikbaarheid gewist?
- wordt de juiste afbeelding gebruikt?
- worden afmetingen en gebruiksinformatie meegewisseld?
- kan client-side selectie oude waarden laten staan?

Zoek in JavaScript naar patronen zoals:

if (variant.price) {
    priceElement.textContent = variant.price;
}

Zonder expliciete `else` is dit een stale-value-risico.

Gewenst patroon:

if (variant.price != null) {
    priceElement.textContent = formatPrice(variant.price);
    priceElement.hidden = false;
} else {
    priceElement.textContent = "";
    priceElement.hidden = true;
}

Pas dit principe toe op alle variantafhankelijke velden.

==================================================
8. VERGELIJKINGSTABELLEN
==================================================

Controleer alle productvergelijkingstabellen.

Per rij moet de backend bij voorkeur expliciet voorbereiden:

- displayvariant;
- displayvariant-ID;
- affiliate-link;
- prijs;
- beschikbaarheid;
- capaciteit, diameter of maat;
- afbeelding wanneer gebruikt;
- rating;
- rating class.

De tabel mag niet zelf via templatefallbacks commerciële data combineren.

Zoek en rapporteer risicopatronen zoals:

{% firstof row.affiliate_url row.product.affiliate_url %}

of:

{{ row.product.price }}

bij producten met varianten.

Verwijder alleen fallbacks wanneer de backend aantoonbaar altijd expliciete
rijvelden levert.

==================================================
9. JSON-LD
==================================================

Controleer alle Product-, Offer- en ItemList-JSON-LD-builders.

Per productfamilie moet gelden:

- één ItemList-item;
- één server-side displayvariant als basis;
- prijs, URL, beschikbaarheid en afbeelding komen van dezelfde variant;
- geen Offer zonder geldige URL en prijs;
- geen prijs van variant A met URL van variant B;
- geen dubbele rankingpositie per variant;
- productfamilierating wordt niet als afzonderlijke variantrating voorgesteld.

Documenteer per categorie welke variant voor JSON-LD wordt gebruikt:

- defaultvariant;
- filtermatchingvariant;
- expliciete displayvariant.

Maak dit consistent met productkaart en tabel waar mogelijk.

10. CLIENT-SIDE SELECTORS
==================================================

Inventariseer alle variant-JavaScriptimplementaties.

Controleer per implementatie:

- scope per productkaart;
- geen globale IDs;
- meerdere kaarten beïnvloeden elkaar niet;
- huidige selectie wordt volledig opnieuw gerenderd;
- ongeldige combinaties worden geblokkeerd;
- ontbrekende velden worden gewist;
- koopknop verdwijnt of wordt uitgeschakeld bij ontbrekende URL;
- prijs van vorige variant blijft niet staan;
- afbeelding van vorige variant blijft niet staan zonder expliciete fallback;
- usage van vorige variant blijft niet staan;
- aria-pressed en disabled-statussen zijn correct.

Centraliseer JavaScript alleen wanneer meerdere categorieën werkelijk dezelfde
componentstructuur gebruiken.

11. CATEGORIEËN ZONDER VARIANTEN
==================================================

Productpagina’s zonder varianten hebben geen cross-variant stale-value-risico.

Controleer daar alleen:

- geen onnodige varianthelper;
- correcte productniveauprijs;
- correcte affiliate-link;
- correcte JSON-LD;
- geen lege commerciële velden.

Voer geen variantrefactor uit op categorieën zonder varianten.

==================================================
12. AUTOMATISCHE FIXES
==================================================

Voer uitsluitend fixes uit die aantoonbaar veilig zijn.

Toegestaan:

- centrale helper corrigeren zodat brondata niet wordt gemuteerd;
- variantvelden expliciet op None zetten;
- templatefallback verwijderen wanneer expliciete backendvelden bestaan;
- ontbrekende `else`-tak toevoegen die oude variantwaarden wist;
- Product/Offer-builder dezelfde resolver laten gebruiken;
- duplicatie vervangen door een bestaande generieke helper;
- tests toevoegen.

Niet toegestaan:

- productdata of prijzen invullen;
- affiliate-links vervangen;
- ontbrekende afbeeldingen raden;
- rankings wijzigen;
- awards of ratings wijzigen;
- nieuwe varianten toevoegen;
- productteksten herschrijven;
- categorieën migreren zonder betrouwbare tests.

13. PROJECTBREDE AUDITCOMMANDO
==================================================

Breid, indien passend, het bestaande auditcommand uit of maak een nieuw
read-only managementcommand:

python manage.py audit_product_variants

Het command moet projectbreed controleren:

- categorieën met varianten;
- in-place mutatie;
- ontbrekende displayvariant;
- meerdere defaultvarianten;
- ontbrekende commerciële velden;
- cross-variant fallbacks;
- templatefallbacks;
- onveilige JavaScriptupdates;
- JSON-LD-mismatches.

Ondersteun minimaal:

python manage.py audit_product_variants

python manage.py audit_product_variants --category vershoudbakjes

python manage.py audit_product_variants --strict

python manage.py audit_product_variants --report

Rapportpad:

docs/audit-product-variants.md

Het command is standaard read-only.
