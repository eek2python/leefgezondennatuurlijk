Implement Phase 2 of the product monitoring system for the Django affiliate website.

IMPORTANT INTENT
Use the existing product data files as the source of truth.
Do NOT invent a new product architecture.
Do NOT auto-publish changes.
Do NOT auto-modify live rankings or content.
This phase should build real monitoring and reporting on top of the current products_<category>.py files.

==================================================
GOALS OF THIS PHASE
==================================================

Build a practical monitoring layer that:

1. loads all current products from the existing products_<category>.py files
2. validates them against the rule system from Phase 1
3. checks data completeness and consistency
4. compares stored availability/price fields against current reachable product page conditions where possible
5. reports products that may need editorial review
6. proposes replacement candidates only as suggestions, never auto-applies them

==================================================
STRICT GUARDRAILS
==================================================

- Do NOT auto-edit any products_<category>.py file
- Do NOT auto-edit rankings_<category>.py
- Do NOT auto-edit content_<category>.py
- Do NOT auto-publish any replacements
- Do NOT weaken the category rules
- Do NOT infer PFAS-free or safety claims if unclear
- If uncertain, flag for manual review
- Preserve the current website rendering and architecture

==================================================
PHASE 2 IMPLEMENTATION TASKS
==================================================

Build the following:

1. Product source loader
2. Field normalization / consistency checks
3. Stored-data validation
4. Product page reachability check
5. Availability consistency check
6. Price consistency / change detection
7. Replacement candidate suggestion support
8. Human-readable reports

==================================================
1. PRODUCT SOURCE LOADER
==================================================

Create a loader that imports and reads all current product dictionaries from the existing category files.

It should support these categories explicitly:
- koekenpannen -> products_koekenpannen.py
- rvs-koekenpannen -> products_rvs_koekenpannen.py
- hapjespannen -> products_hapjespannen.py
- wokpannen -> products_wokpannen.py
- snijplanken -> products_snijplanken.py
- airfryers -> products_airfryers.py
- vershoudcontainers -> products_vershoudcontainers.py

Requirements:
- build an explicit category source registry
- load product dicts safely
- fail gracefully if a category file or variable is missing
- report missing categories instead of crashing

==================================================
2. FIELD NORMALIZATION / CONSISTENCY CHECKS
==================================================

Create a normalization and consistency layer for currently stored fields.

Check and normalize where possible:
- brand
- material
- diameter
- capacity
- price
- currency
- availability
- affiliate_url
- image
- image_path
- rating
- rating_count
- price_range

Important:
- do not overwrite source files
- only normalize in-memory for validation/reporting purposes
- flag suspicious or missing values

Examples of checks:
- price should be numeric if present
- currency should normally be EUR
- availability should be one of a controlled list like:
  - InStock
  - OutOfStock
  - PreOrder
  - LimitedAvailability
  - Unknown
- affiliate_url should be a non-placeholder URL
- image + image_path together should form a plausible static asset path
- rating should be numeric and within expected range
- price_range should match the stored price approximately if possible

==================================================
3. STORED-DATA VALIDATION
==================================================

Extend the Phase 1 rule engine so it now validates the actual stored product objects.

Per product, validate:
- category fit
- material fit
- rule compliance
- missing required metadata
- brand diversity risk
- suspicious values
- mismatch between product name/description/material/features and category expectations

Examples:
- RVS product in keramische koekenpannen -> flag
- unclear PFAS positioning in PFAS-vrije category -> manual review
- snijplank with glass/plastic signals -> invalid
- vershoudbakje that is not glass -> invalid
- broken or placeholder affiliate_url -> flag

==================================================
4. PRODUCT PAGE REACHABILITY CHECK
==================================================

Implement a safe HTTP product-page check for affiliate_url / product page URLs.

Requirements:
- perform lightweight HEAD or GET checks
- follow redirects safely
- time out safely
- do not hammer websites
- use respectful request behavior
- classify page status:
  - OK
  - REDIRECTED
  - BROKEN
  - BLOCKED
  - UNKNOWN

If live checks are restricted in the current runtime, create the implementation structure and provide a testable fallback mode.
But prefer real checks if technically possible within the environment.

Store report info such as:
- final URL if redirected
- HTTP status code
- page reachable yes/no
- notes

==================================================
5. AVAILABILITY CONSISTENCY CHECK
==================================================

Use the stored field `availability` as the current site value.
Then compare it, where possible, with signals from the product page.

Important:
- do not try to do fragile deep scraping unless simple availability signals are feasible
- if the page cannot be reliably interpreted, classify as Unknown and flag for manual review
- if stored availability is InStock but page is clearly unavailable or broken, flag it
- if stored availability is OutOfStock but page appears active and available, flag for editorial check

Output values:
- stored_availability
- detected_availability
- availability_consistency: MATCH / MISMATCH / UNKNOWN

==================================================
6. PRICE CONSISTENCY / CHANGE DETECTION
==================================================

Use the stored field `price` as the website’s current recorded price.
Then compare it, where possible, with a newly detected live price.

Requirements:
- if live price cannot be reliably extracted, do not invent it
- if a live price is found:
  - compare against stored price
  - compute price_change_pct
- flag if:
  - price missing
  - price invalid
  - large change threshold exceeded (configurable, e.g. 10%)
- keep this report-only, never auto-update product files

Output values:
- stored_price
- detected_price
- currency
- price_change_pct
- price_alert: True/False

==================================================
7. REPLACEMENT CANDIDATE SUGGESTION SUPPORT
==================================================

Build on the Phase 1 candidate suggestion logic.

If a product is flagged for replacement because of:
- invalid category fit
- unavailable / broken page
- severe rule mismatch
- clearly outdated status

Then suggest replacement candidates from a candidate pool.

Requirements:
- do not auto-search the full internet unless current project infrastructure already supports it
- first support replacement suggestions from an internal candidate pool if available
- if no candidate pool exists yet, structure the code so a future candidate source can be plugged in
- output suggestions based on:
  1. category match
  2. material/safety fit
  3. size/capacity match
  4. price segment
  5. rating strength
  6. availability
  7. brand diversity

Very important:
- suggestions only
- no automatic insertion into rankings
- if no safe suggestion exists, manual review required
