FASE 3 — CENTRALE PRICE_RANGE-HELPER

Breid de bestaande helper uit zodat deze categoriegebonden grenzen gebruikt.

Voorkeursvorm:

from decimal import Decimal, InvalidOperation


VALID_PRICE_RANGES = {"€", "€€", "€€€", "€€€€"}


def normalize_price(value):
    if value is None or value == "":
        return None

    try:
        return Decimal(str(value))
    except (InvalidOperation, TypeError, ValueError):
        return None


def calculate_price_range(price, category_key):
    normalized_price = normalize_price(price)

    if normalized_price is None:
        return None

    thresholds = PRICE_RANGE_THRESHOLDS.get(category_key)

    if thresholds is None:
        return None

    level_2, level_3, level_4 = thresholds

    if normalized_price < level_2:
        return "€"

    if normalized_price < level_3:
        return "€€"

    if normalized_price < level_4:
        return "€€€"

    return "€€€€"

Pas namen en locatie aan de bestaande architectuur aan.

FASE 5 — VARIANTREGELS

Hergebruik de bestaande veilige variantselectie.

Regels:

Wanneer de productkaart een specifieke display_variant gebruikt, moet de audit dezelfde prijs gebruiken.

Gebruik geen prijs van een willekeurige andere variant.

Wanneer een geselecteerde variant geen prijs heeft, meld dat volgens de bestaande auditlogica.

Gebruik alleen productniveau-fallback wanneer de bestaande commerciële resolver dit expliciet toestaat.

De price_range moet overeenkomen met de prijs die daadwerkelijk publiek voor het product of de geselecteerde variant wordt gebruikt.

Voorkom dat de audit een variantprijs vergelijkt met een price_range van een andere variant.

Breid indien nodig de bestaande resolve_commercial_fields of vergelijkbare helper uit, maar maak geen afzonderlijke variantresolver voor deze audit.

ACCEPTATIECRITERIA

De taak is voltooid wanneer:

hapjespannen categoriegebonden prijsgrenzen gebruiken;

de grenzen €40, €70 en €110 correct worden toegepast;

exacte grensbedragen in de volgende categorie vallen;

dezelfde centrale helper wordt gebruikt als voor keramische koekenpannen;

er geen dubbele prijslogica ontstaat;

varianten veilig worden afgehandeld;

het bestaande auditdashboard mismatches toont;

keramische-koekenpangrenzen ongewijzigd blijven;

bestaande productdata niet automatisch wordt herschreven;

alle nieuwe tests en de volledige bestaande testsuite slagen.
